# viewr 0.1.1

A patch release over the first public preview. It fixes what first-contact
testing of the v0.1.0 Linux archive found: a launch that produced no window and
said nothing about why. No feature scope changed, and the privacy boundary is
unchanged.

It also carries the fixes and internal reliability work completed on `main`
since v0.1.0. That work moved state transitions into covered pure seams with
user-visible behavior deliberately unchanged, so it adds no capability here. The
**v0.2.0** reliability milestone and its exit criteria remain open; this patch
does not close them.

## Fixed

- **A failed launch is now visible and non-zero.** When the window or its GPU
  surface cannot be created, viewr prints one actionable message on standard
  error and exits non-zero. v0.1.0 logged that only under `RUST_LOG` and exited
  successfully, so `viewr photo.jpg` looked like a no-op.
- **Linux launches check the libraries the windowing backend loads at run
  time.** A missing one names its soname and the package to install on Debian,
  Ubuntu, Fedora, RHEL, and Arch instead of aborting inside the dynamic loader.
  v0.1.0 ended in a panic naming `libxkbcommon-x11.so` that `ldd` could not
  predict. A host with no desktop session is told so plainly, and Wayland hosts
  that fall back to X11 are not blocked.
- **`viewr doctor` no longer reports a healthy install on a host that cannot
  open a window.** Window presentation is its own section: detected session,
  required libraries, and an explicit note that a GPU surface is proven only
  when viewr opens a window. A session that cannot load those libraries is a
  critical failure. The missing-worker warning now describes the shipped
  two-binary layout rather than an optional cargo feature.
- **`--help` and `-h` are reserved on every subcommand.** `viewr doctor --help`,
  `viewr benchmark --help`, `viewr open --help`, `viewr update --help`, and
  `viewr performance-probe --help` print help for that command instead of
  running it, failing on a directory, or opening the GUI on the literal flag.
  `viewr help <command>` prints the same screens, and subcommands reject
  arguments they do not accept.
- **A mistyped command reports itself.** An unknown first word that is not an
  existing path, and does not look like one, prints `'word' is not a viewr
  command` and exits 2 instead of starting the GUI. Files, folders, Open With,
  and drag-to-shortcut are unchanged.
- **`viewr-decode` explains itself instead of hanging.** Running the decode
  worker by hand, or with any argument, prints a short explanation and exits
  rather than waiting for a protocol frame that will never arrive.
- **Help examples use the path separator of the platform reading them.**
- The Unix installer prints the `viewr doctor` report when staged binaries fail
  it, so a missing desktop library is visible instead of swallowed.
- Finishing Trash no longer forces navigation when you already moved to another
  surviving image while the move ran, and in-progress Trash uses the persistent
  operation status instead of stacking a second busy toast.

## Performance

- Delete feels closer to ordinary navigation. Trash no longer lists the whole
  system Trash before the move just to prepare Undo, and the next image reuses an
  already-prefetched decode instead of clearing the neighbor cache first. Exact
  Undo still binds a receipt after the move when the platform can prove it.

## Security

- The transitive `webbrowser` dependency moves to 1.2.2 for `RUSTSEC-2026-0257`.
  viewr has no HTTP or TLS client; the crate arrives through the egui hyperlink
  path, and the advisory floor is enforced rather than waived.

## Documentation

- The [installation guide](../INSTALL.md) lists the Linux runtime libraries each
  desktop session loads dynamically, with the package name per distribution, and
  states what `viewr doctor` does and does not prove about opening a window.
- The README states the current rating write scope beside the controls table:
  Windows writes ratings to supported JPEG files, while macOS and Linux read
  existing ratings and filter by them.
- The installation and verification guides note that `gh attestation` and
  `gh release verify` need GitHub CLI 2.49 or newer, and name the SHA-256
  sidecar and internal per-file manifest as the evidence available without them.

## Install and verify

Download the archive for your platform or use the fixed-version installer
command in the [installation guide](../INSTALL.md). Every archive and installer
script has a SHA-256 sidecar and a GitHub build-provenance attestation. Archives
also contain a canonical per-file manifest.

The application itself has no network client. Installer scripts are separate,
foreground tools that contact only the official GitHub repository after you run
them. Updates are manual and explicit.

On Linux, a desktop session needs `libxkbcommon` plus either the X11 keyboard
and Xlib libraries or `libwayland-client`, and a working GPU driver or the Mesa
software renderer. `viewr doctor` reports exactly which of these are missing.

## Preview limits

These portable archives are not Authenticode-signed on Windows or notarized on
macOS. Normal operating-system trust warnings may appear. Do not disable
platform security controls to force a launch.

The remaining 1.0 gates are unchanged by this patch: code signing and
notarization, human Narrator, VoiceOver, and Orca acceptance,
representative-hardware checks, and per-display color correctness. Optional
AVIF, HEIC, and RAW decoders are not enabled in these default archives.
